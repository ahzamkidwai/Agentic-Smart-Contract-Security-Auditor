# MOD-012: MEV / Sandwich Attacks (Insufficient Slippage Protection)

## Vulnerability Description
Miner Extractable Value (MEV) includes strategies like "sandwich attacks." When a user submits a transaction to an AMM (like Uniswap) to swap a large amount of tokens, their transaction affects the price. Searcher bots spot this in the mempool, place a "buy" order right before the user (front-running), causing the price to jump. The user buys at the worse price. The bot then places a "sell" order immediately after (back-running), pocketing the difference. This exploits contracts that execute swaps without setting strict `minAmountOut` (slippage) requirements.

## Severity
High

## Detection Rules & Indicators
- Calls to AMM routers (e.g., `swapExactTokensForTokens`) where `amountOutMin` is set to `0` or calculated dynamically in the same transaction without a trusted oracle.
- Lack of a `deadline` parameter (allowing miners to hold the transaction and execute it when market conditions are unfavorable to the user).

## Vulnerable Example
```solidity
contract VulnerableSwapper {
    IUniswapV2Router02 public router;

    function swapTokens(uint amountIn, address[] calldata path) public {
        // Vulnerable: amountOutMin is 0 (100% slippage allowed). 
        // A sandwich bot will extract almost all value from this swap.
        // Vulnerable: deadline is block.timestamp, which never expires.
        router.swapExactTokensForTokens(
            amountIn,
            0, 
            path,
            msg.sender,
            block.timestamp 
        );
    }
}
```

## Safe Example / Remediation
```solidity
contract SafeSwapper {
    IUniswapV2Router02 public router;

    // Fix: Force the caller to provide a minimum acceptable output and a deadline.
    function swapTokens(
        uint amountIn, 
        uint amountOutMin, 
        uint deadline, 
        address[] calldata path
    ) public {
        router.swapExactTokensForTokens(
            amountIn,
            amountOutMin, 
            path,
            msg.sender,
            deadline 
        );
    }
}
```

## False-Positive Conditions & Counterexamples
- **Zero Slippage on Exact Output**: Functions like `swapTokensForExactTokens` focus on fixing the *output* and let the *input* fluctuate up to a maximum. If `amountInMax` is reasonably set, it is **safe**.
- **Internal Oracles**: If the contract calculates `minAmountOut` securely on-chain using an external Chainlink oracle right before the swap, this is an excellent, **safe** pattern.
- **Liquidation Mechanics**: In some lending protocols, liquidators are intentionally allowed high slippage as a reward for securing the protocol. This is a design choice, not a strict vulnerability.

## Solidity-Version Notes
Applies to all versions.

## Related Detectors
- Manual review. Look for hardcoded `0`s in swap router arguments.
