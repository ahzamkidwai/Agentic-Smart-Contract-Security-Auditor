# SWC-115: Authorization through tx.origin

## Vulnerability Description
A contract uses `tx.origin` (the original EOA that initiated the transaction) for access control instead of `msg.sender` (the direct caller). If a user with privileges interacts with a malicious contract, that malicious contract can call the vulnerable contract. Since `tx.origin` remains the privileged user, the access control check passes, allowing the malicious contract to drain funds or alter state.

## Severity
High

## Detection Rules & Indicators
- Usage of `require(tx.origin == owner)` or using `tx.origin` to check privileges.

## Vulnerable Example
```solidity
contract VulnerableWallet {
    address public owner;

    constructor() { owner = msg.sender; }

    // Vulnerable: Relies on tx.origin
    function withdraw(address payable dest, uint amount) public {
        require(tx.origin == owner); // Malicious contract can bypass this!
        dest.transfer(amount);
    }
}
```

## Safe Example / Remediation
```solidity
contract SafeWallet {
    address public owner;

    constructor() { owner = msg.sender; }

    // Safe: Uses msg.sender
    function withdraw(address payable dest, uint amount) public {
        require(msg.sender == owner); 
        dest.transfer(amount);
    }
}
```

## False-Positive Conditions & Counterexamples
- **Phishing Protection Check**: A very common and safe use of `tx.origin` is preventing smart contracts from calling a function. By asserting `require(tx.origin == msg.sender)`, a contract guarantees that the caller is an EOA (Externally Owned Account) and not a smart contract. This is **safe** and intended behavior, not an SWC-115 vulnerability.
- **Logging / Tracking**: Using `tx.origin` to log the original user in an event or trace transaction flow is safe, provided it is not used for authentication.

## Solidity-Version Notes
Applies to all versions. Vitalik Buterin has suggested eventually removing or changing `tx.origin`, so relying on it is generally discouraged.
