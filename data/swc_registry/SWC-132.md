# SWC-132: Unexpected Ether Balance

## Vulnerability Description
A contract's logic assumes its Ether balance (`address(this).balance`) can only change through its own deposit/withdrawal functions, or assumes the balance will always equal exactly zero. However, anyone can forcefully send Ether to a contract, bypassing its `receive()` or `fallback()` functions. This is done by creating another contract and calling `selfdestruct(target_address)`, or by specifying the contract as a block reward coinbase. If the contract relies on an exact balance check, this force-fed ETH will break its internal invariants, causing it to freeze or fail.

## Severity
Medium / High

## Detection Rules & Indicators
- Strict equality checks involving `address(this).balance`, such as `require(address(this).balance == 0)` or `require(address(this).balance == internalAccounting)`.

## Vulnerable Example
```solidity
contract Game {
    uint public targetAmount = 7 ether;
    address public winner;

    function play() public payable {
        require(msg.value == 1 ether);
        
        // Vulnerable: If someone force-sends 0.1 ETH, the balance will jump from 
        // 6 to 7.1, bypassing 7 exactly. The game is permanently broken.
        require(address(this).balance <= targetAmount);
        
        if (address(this).balance == targetAmount) {
            winner = msg.sender;
        }
    }
}
```

## Safe Example / Remediation
```solidity
contract SafeGame {
    uint public targetAmount = 7 ether;
    uint public currentBalance;
    address public winner;

    function play() public payable {
        require(msg.value == 1 ether);
        
        // Fix: Use internal accounting variable instead of address(this).balance
        currentBalance += msg.value;
        require(currentBalance <= targetAmount);
        
        if (currentBalance == targetAmount) {
            winner = msg.sender;
        }
    }
}
```

## False-Positive Conditions & Counterexamples
- **Internal Accounting**: If a contract uses a state variable (e.g., `uint public totalDeposits`) to track ETH instead of `address(this).balance`, it is **safe** from this attack.
- **Sweeper Functions**: A contract that uses `address(this).balance - totalDeposits` to withdraw "excess" force-fed ETH is **safe** and utilizing best practices.
- **Inequality Checks**: `require(address(this).balance >= amount)` is perfectly safe, because force-fed ETH will only increase the balance, keeping the inequality true. The vulnerability primarily exists with strict `==` checks.

## Solidity-Version Notes
Applies to all versions. Note: EIP-6780 (Dencun) deprecated contract-killing `selfdestruct`, but it *still* allows force-feeding ETH, so this vulnerability remains highly relevant.
