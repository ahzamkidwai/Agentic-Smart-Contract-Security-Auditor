# MOD-009: Unauthorized Upgrades / Uninitialized Proxies

## Vulnerability Description
Proxy contracts usually delegate initialization to an `initialize()` function rather than a `constructor` (since constructors don't affect proxy storage). If the proxy or the implementation logic contract is left uninitialized, an attacker can call `initialize()` to claim ownership. Furthermore, in UUPS patterns, the upgrade logic resides in the implementation itself. If the implementation is not initialized, an attacker can initialize it directly, call `upgradeToAndCall` with a malicious `selfdestruct` contract, and destroy the implementation, permanently bricking all proxies relying on it.

## Severity
High

## Detection Rules & Indicators
- Missing `_disableInitializers()` in the constructor of an upgradeable implementation contract.
- `initialize()` functions lacking the `initializer` modifier.
- Missing access control (`onlyOwner` / `onlyRole`) on `upgradeTo` functions.

## Vulnerable Example
```solidity
import "@openzeppelin/contracts-upgradeable/proxy/utils/Initializable.sol";
import "@openzeppelin/contracts-upgradeable/proxy/utils/UUPSUpgradeable.sol";

contract VulnerableImplementation is Initializable, UUPSUpgradeable {
    address public owner;

    // Vulnerable: Anyone can call this on the implementation contract directly!
    function initialize() public initializer {
        owner = msg.sender;
    }

    function _authorizeUpgrade(address newImplementation) internal override {
        require(msg.sender == owner, "Unauthorized");
    }
}
```
*Attack: Attacker calls `initialize()` directly on the implementation contract (not the proxy). They become the owner of the implementation. They then upgrade the implementation to a contract that self-destructs. The proxy is now bricked.*

## Safe Example / Remediation
```solidity
contract SafeImplementation is Initializable, UUPSUpgradeable {
    address public owner;

    /// @custom:oz-upgrades-unsafe-allow constructor
    constructor() {
        // Fix: Automatically locks the implementation contract from being initialized directly
        _disableInitializers(); 
    }

    function initialize() public initializer {
        owner = msg.sender;
    }

    function _authorizeUpgrade(address newImplementation) internal override {
        require(msg.sender == owner, "Unauthorized");
    }
}
```

## False-Positive Conditions & Counterexamples
- **Transparent Proxies**: In the Transparent Proxy pattern, upgrade logic is handled by a ProxyAdmin, not the implementation. Destroying the implementation is still bad, but the upgrade mechanism itself is not inherently vulnerable to UUPS-style attacks.
- **`_disableInitializers` used**: If the constructor includes `_disableInitializers()`, the contract is **safe** from direct initialization attacks.

## Solidity-Version Notes
Applies to all versions using proxy patterns.
