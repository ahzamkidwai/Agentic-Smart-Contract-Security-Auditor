# SWC-114: Transaction Order Dependence (Front-Running)

## Vulnerability Description
A contract's state or behavior depends on the order in which transactions are included in a block. Since miners/validators determine block order, and transactions are visible in the mempool before execution, an attacker can monitor the mempool and submit a transaction with a higher gas price (or use MEV bots) to execute their transaction *before* a victim's transaction. Common examples include ERC20 token approvals and AMM slippage.

## Severity
Medium / High (Context dependent)

## Detection Rules & Indicators
- AMM swaps (Uniswap, SushiSwap) without `minAmountOut` (slippage protection) or `deadline` checks.
- The classic ERC20 `approve` race condition.
- Any "first-come, first-served" reward mechanics with predictable solutions (e.g., simple puzzle solvers).

## Vulnerable Example (ERC20 Approve Race Condition)
```solidity
contract Token {
    mapping(address => mapping(address => uint)) public allowance;

    // Vulnerable: Alice approves Bob for 100. Then she wants to change it to 50.
    // She sends approve(Bob, 50). Bob sees this, front-runs and spends the 100.
    // Then the 50 gets approved, and Bob spends 50 more. Total spent: 150.
    function approve(address spender, uint amount) public {
        allowance[msg.sender][spender] = amount;
    }
}
```

## Safe Example / Remediation
```solidity
contract SafeToken {
    mapping(address => mapping(address => uint)) public allowance;

    // Fix: increase/decrease allowance instead of overwriting
    function increaseAllowance(address spender, uint addedValue) public {
        allowance[msg.sender][spender] += addedValue;
    }
    
    function decreaseAllowance(address spender, uint subtractedValue) public {
        allowance[msg.sender][spender] -= subtractedValue;
    }
}
```

## False-Positive Conditions & Counterexamples
- **Slippage Protection Used**: If an AMM swap uses a reasonable `minAmountOut` parameter provided by the user, front-running (sandwich attacks) is mitigated.
- **Commit-Reveal Schemes**: If the contract uses a commit-reveal scheme (where the user submits a hash first, then reveals the answer later), it is protected from front-running.
- **SafeERC20 / increaseAllowance**: Modern contracts use `safeIncreaseAllowance` which prevents the race condition.

## Solidity-Version Notes
Applies to all versions.
