# SWC-116: Block values as a proxy for time

## Summary
A contract uses `block.timestamp` (or older block-number-based tricks) as
the sole source of "current time" for security-critical logic - e.g.
picking a pseudo-random winner, gating a time-locked withdrawal, or
resolving a bet.

## Why it matters
Block miners/validators have some leeway to influence the exact timestamp
of a block they propose. For most use cases (a 24-hour vesting cliff) this
tiny manipulation window doesn't matter, but for anything where a small
timing shift changes an outcome - like using `block.timestamp` as a source
of randomness - it can be exploited to bias the result in the miner's
favor.

## Typical patterns Slither flags
- `block.timestamp` used directly inside a conditional that gates a
  high-value outcome (payouts, randomness seeding, auction resolution).

## Typical fix
- Avoid using `block.timestamp` as a randomness source entirely; use a
  verifiable randomness solution (e.g. Chainlink VRF) instead.
- For time-lock logic, keep tolerance windows wide (minutes/hours rather
  than seconds) so the small manipulation window miners have doesn't
  matter.
