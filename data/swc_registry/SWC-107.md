# SWC-107: Reentrancy

## Summary
A contract makes an external call (e.g. sending ETH, calling another
contract) before it has finished updating its own internal state. The
called address - which can be attacker-controlled - can call back into the
original function during that external call and re-enter it while the
state is still stale, repeating an action (like a withdrawal) multiple
times before the balance is ever decremented.

## Why it matters
This is the vulnerability class behind the 2016 DAO hack and remains one of
the most common causes of major fund-draining exploits in DeFi. A single
reentrant withdrawal function can be enough to empty an entire contract's
balance.

## Typical patterns Slither flags
- `reentrancy-eth`: external call that sends ETH happens before a state
  variable (like a balance mapping) is updated.
- `reentrancy-no-eth` / `reentrancy-events`: same ordering issue but for
  calls that don't move ETH, or where only event emission order is
  affected - lower severity but still worth fixing.

## Typical fix
- Follow the checks-effects-interactions pattern: update all state
  (balances, flags) *before* making the external call.
- Add a reentrancy guard, e.g. OpenZeppelin's `ReentrancyGuard` /
  `nonReentrant` modifier, as defense in depth.
