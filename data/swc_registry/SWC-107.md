# SWC-107: Reentrancy (Classic / Single-Function)

## Vulnerability Description
A contract makes an external call to an untrusted address before finishing the update of its own internal state. The called address can use its fallback function to call back into the original function. Because the state was not updated before the external call, the internal checks (e.g., balance > 0) still pass, allowing the attacker to drain funds or corrupt state.

## Severity
High

## Detection Rules & Indicators
- External calls (`.call{value: x}("")`, `.transfer()`, ERC20 `transfer`, ERC777 hooks, etc.) occurring *before* a state variable (like a balance) is updated.
- Violation of the Checks-Effects-Interactions (CEI) pattern.

## Exploit Conditions
All of the following must hold for this to be practically exploitable:
1. The external call target is attacker-controlled (directly `msg.sender`,
   or a contract address the attacker can point at their own contract).
2. The callee has a fallback/receive function that can call back into the
   vulnerable contract (trivial for `msg.sender.call{value: amount}("")`
   — any contract wallet has one).
3. A state variable the re-entered call path depends on (e.g. the sender's
   balance) is still unchanged at the moment of re-entry — i.e. it's
   written *after* the call, not before.
4. There is no reentrancy guard (`nonReentrant`) active on the call path.
If any of these doesn't hold — e.g. the callee is a known non-reentrant
contract, or state is already updated — the *ordering* pattern may still
be visible in the code but is not exploitable the same way; note that
distinction rather than treating every call-before-write as equally risky.

## Vulnerable Example
This is the project's own `VulnerableBank.withdraw()` test contract —
canonical example of the ordering violation:
```solidity
contract VulnerableBank {
    mapping(address => uint256) public balances;

    function deposit() external payable {
        balances[msg.sender] += msg.value;
    }

    function withdraw(uint256 amount) external {
        require(balances[msg.sender] >= amount, "insufficient balance");

        // Vulnerability:
        // External call happens BEFORE state update.
        (bool ok, ) = msg.sender.call{value: amount}("");
        require(ok, "transfer failed");

        balances[msg.sender] -= amount;
    }
}
```
Note: `require(ok, "transfer failed")` checking the call's return value
does NOT make this safe — that only addresses SWC-104 (unchecked return
value), a completely different concern. The reentrancy risk here is
purely about *ordering*: `balances[msg.sender] -= amount` still executes
after the external call, so a re-entrant call during that `.call{}` can
observe the stale (higher) balance and withdraw again before it's
decremented.

## Safe Example / Remediation
This is the project's own `SafeVault.withdraw()` test contract — same
call, correct order:
```solidity
contract SafeVault {
    mapping(address => uint256) public balances;

    function withdraw(uint256 amount) external {
        require(balances[msg.sender] >= amount, "insufficient balance");
        balances[msg.sender] -= amount; // state update before external call
        (bool ok, ) = msg.sender.call{value: amount}("");
        require(ok, "transfer failed");
    }
}
```
The call itself is identical to VulnerableBank's — same low-level
`.call{value: amount}("")`, same return-value check. The only difference
is that `balances[msg.sender] -= amount` now happens BEFORE the external
call, so even unlimited reentrancy during that call sees the
already-decremented balance and `require(balances[msg.sender] >= amount)`
fails on any repeat attempt. This pair (VulnerableBank vs SafeVault) is
the canonical minimal contrast: identical low-level call, only the
ordering differs, only one is exploitable.

## False-Positive Conditions & Counterexamples
- **Checks-Effects-Interactions (CEI)**: If the state is updated *before* the external call, it is **safe**, even if there's an external call. The RAG must not flag every `call` as reentrancy if state is already updated.
- **Reentrancy Guard**: If the function has a `nonReentrant` modifier (e.g., from OpenZeppelin), it is **safe**, even if the CEI pattern is violated.
- **Trusted Callee**: If the external call is to a known, trusted contract that is guaranteed not to re-enter (e.g., calling `WETH.withdraw`), it is generally safe (though CEI is still preferred).
- **No State Mutation After Call**: If the contract makes an external call, but does *not* mutate state afterward (and does not rely on cross-function state), it is usually not exploitable for classic reentrancy.

## Solidity-Version Notes
Applies to all versions.
