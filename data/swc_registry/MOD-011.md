# MOD-011: Token Security & Weird ERC20s (Fee-on-Transfer, Rebasing)

## Vulnerability Description
Many smart contracts assume all ERC20 tokens behave exactly like standard WETH or DAI: transferring 100 tokens deducts 100 from the sender and adds exactly 100 to the receiver. However, "weird" tokens exist:
1. **Fee-on-transfer tokens**: Deduct a percentage on every transfer. Receiving 100 tokens might actually only deliver 98 tokens.
2. **Rebasing tokens (AMPL, stETH)**: Balances fluctuate globally over time without explicit transfers.
3. **Tokens without return booleans (USDT)**: Do not return a standard `bool` on transfer.
If a contract (like an AMM or Lending pool) assumes the amount sent is the amount received, its internal accounting will become severely desynced, leading to insolvency.

## Severity
Medium / High (Depending on the protocol's exposure to arbitrary tokens)

## Detection Rules & Indicators
- The contract updates internal accounting based on the `amount` variable passed as a function argument, rather than checking the *actual* balance difference before and after the transfer.

## Vulnerable Example
```solidity
contract VulnerablePool {
    mapping(address => uint) public deposits;

    function deposit(ERC20 token, uint amount) public {
        // Vulnerable: If token takes a 10% fee, the contract only receives 90,
        // but credits the user for 100! User can withdraw 100 later, draining pool.
        token.transferFrom(msg.sender, address(this), amount);
        deposits[msg.sender] += amount; 
    }
}
```

## Safe Example / Remediation
```solidity
contract SafePool {
    mapping(address => uint) public deposits;

    function deposit(ERC20 token, uint amount) public {
        // Fix: Check balance before and after
        uint balanceBefore = token.balanceOf(address(this));
        token.transferFrom(msg.sender, address(this), amount);
        uint balanceAfter = token.balanceOf(address(this));
        
        uint actualReceived = balanceAfter - balanceBefore;
        
        deposits[msg.sender] += actualReceived;
    }
}
```

## False-Positive Conditions & Counterexamples
- **Whitelisted Tokens**: If a protocol only allows deposits from a strict whitelist of known standard tokens (e.g., WETH, USDC), the "balance before and after" check is unnecessary and wastes gas. In this context, relying on the `amount` parameter is **safe**.
- **Yield-Bearing Wrappers**: If rebasing tokens are explicitly prohibited, or if users are forced to use non-rebasing wrappers (like `wstETH` instead of `stETH`), the protocol is **safe**.

## Solidity-Version Notes
Applies to all versions.

## Related Detectors
- Manual review required. (Slither has `erc20-interface` but doesn't usually catch fee-on-transfer logic).
