# MOD-003: Read-Only Reentrancy

## Vulnerability Description
Read-only reentrancy occurs when a contract makes an external call while its state is temporarily inconsistent (e.g., during a swap or withdrawal). An attacker re-enters, but instead of calling a state-mutating function, they call a `view` function (like `getReserves()` or `getPrice()`) on the vulnerable contract. A *third-party* protocol that integrates with the vulnerable contract might rely on this `view` function for its own logic. The attacker manipulates the third-party protocol using the distorted price/state reported by the `view` function.

## Severity
High (For the third-party protocol), Medium (For the source protocol, if it doesn't harm them directly).

## Detection Rules & Indicators
- A `view` function that calculates prices, reserves, or virtual balances based on state variables that are temporarily out of sync during execution of another function.
- Third-party protocols that rely on spot AMM prices or vault share prices during execution without checking if the AMM/Vault is currently unlocked.

## Vulnerable Example (Source Protocol)
```solidity
contract VulnerableAMM {
    uint public reserve0;
    uint public reserve1;
    
    // View function used by other protocols as an oracle
    function getSpotPrice() public view returns (uint) {
        return reserve1 / reserve0; 
    }
    
    function removeLiquidity() public {
        // 1. Send tokens to user (Interaction)
        token0.transfer(msg.sender, amount0); 
        
        // Attacker intercepts the ERC777 callback here. 
        // reserve0 hasn't been updated yet, but the token balance of the AMM is lower!
        // The attacker calls a 3rd party lending platform that calls getSpotPrice().
        
        // 2. Update state (Effect) - Violates CEI!
        reserve0 -= amount0;
        reserve1 -= amount1;
    }
}
```

## Safe Example / Remediation
```solidity
contract SafeAMM {
    uint private _status = 1;
    
    modifier nonReentrant() {
        require(_status == 1, "REENTRANCY");
        _status = 2;
        _;
        _status = 1;
    }

    // Fix: Add the nonReentrant guard to VIEW functions!
    // Or, follow CEI strictly in the mutating functions.
    function getSpotPrice() public view returns (uint) {
        require(_status == 1, "Read-Only Reentrancy Protection");
        return reserve1 / reserve0;
    }
}
```

## False-Positive Conditions & Counterexamples
- **Strict CEI**: If the source protocol perfectly updates all state *before* any external token transfers (even ERC20/ERC777), the `view` functions will never report an inconsistent state. This is **safe**.
- **No Third-Party Reliance**: If the `view` function is not used as an oracle or by any other contract (e.g., just a frontend helper), it cannot be exploited for read-only reentrancy.
- **TWAP Oracles**: Using Time-Weighted Average Prices (TWAP) instead of spot prices mitigates read-only reentrancy because instantaneous state changes don't significantly affect the average.

## Solidity-Version Notes
Applies to all versions.

## Related Detectors
- Custom detectors in tools like Slither or manually hunting for `view` functions that lack reentrancy guards in DeFi primitives.
