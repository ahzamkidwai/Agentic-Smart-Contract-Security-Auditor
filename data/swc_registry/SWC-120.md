# SWC-120: Weak Sources of Randomness from Chain Attributes

## Vulnerability Description
Using blockchain attributes like `block.timestamp`, `blockhash`, `block.difficulty` (or `block.prevrandao`), or `msg.sender` as seeds for random number generation (RNG). Because miners/validators have some control over block parameters or can choose not to publish a block if the randomness doesn't favor them, they can manipulate the RNG. Additionally, other contracts in the same block can easily read these values and predict the outcome before interacting.

## Severity
High (If used in gambling/lotteries), Low (If used for non-critical visual generation like NFTs).

## Detection Rules & Indicators
- Usage of `keccak256(abi.encodePacked(blockhash(block.number - 1), block.timestamp))` or similar patterns to decide winners or critical random outcomes.

## Vulnerable Example
```solidity
contract Lottery {
    function play() public payable {
        // Vulnerable: Miners can predict or influence this
        uint random = uint(keccak256(abi.encodePacked(block.timestamp, msg.sender))) % 100;
        
        if (random == 0) {
            msg.sender.transfer(address(this).balance);
        }
    }
}
```

## Safe Example / Remediation
```solidity
// Fix: Use an external oracle like Chainlink VRF for verifiable randomness.
import "@chainlink/contracts/src/v0.8/VRFConsumerBase.sol";

contract SafeLottery is VRFConsumerBase {
    // ... requestRandomness logic ...
    
    function fulfillRandomness(bytes32 requestId, uint256 randomness) internal override {
        // Safe: Randomness is securely provided by Chainlink nodes
        uint randomOutcome = randomness % 100;
    }
}
```

## False-Positive Conditions & Counterexamples
- **Non-Critical Randomness**: If weak randomness is used to assign a random background color to an NFT during mint, or scatter spawn locations in a low-stakes game, the risk is negligible. While technically a "weak source", it's **safe** in context.
- **Commit-Reveal Mechanisms**: If the protocol combines blockhashes with a secret user commit-reveal scheme (where the user commits to a hash, a future blockhash is drawn, and then the user reveals), it can be highly secure without an external oracle.

## Solidity-Version Notes
Applies to all versions. Note that in Ethereum Proof of Stake, `block.difficulty` has been renamed to `block.prevrandao`, which provides slightly better (but still manipulable by proposers) randomness.
