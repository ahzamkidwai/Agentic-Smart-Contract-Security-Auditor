# SWC-124: Write to Arbitrary Storage Location

## Vulnerability Description
A smart contract allows an unauthorized user to write data to arbitrary storage slots. Because Solidity packs variables sequentially into storage, an attacker can calculate the exact slot representing the contract's `owner` or a `balance` mapping and overwrite it, granting themselves admin privileges or infinite tokens.

## Severity
High

## Detection Rules & Indicators
- Assembly blocks `assembly { sstore(slot, value) }` where `slot` is derived from user input.
- Uninitialized storage pointers (in Solidity versions prior to 0.5.0) where a struct storage pointer defaults to slot 0 and overwrites state variables.
- Array out-of-bounds writes (in older compilers or when using unchecked assembly).

## Vulnerable Example (Uninitialized Storage Pointer - Pre 0.5.0)
```solidity
pragma solidity ^0.4.24;

contract Vulnerable {
    address public owner;
    
    struct User { uint id; }
    mapping(address => User) users;

    function register() public {
        // Vulnerable: 'user' is a storage pointer but is uninitialized.
        // It points to slot 0 (which is 'owner').
        User user; 
        user.id = 1; // Overwrites the 'owner' address with 1!
    }
}
```

## Safe Example / Remediation
```solidity
pragma solidity ^0.8.0;

contract Safe {
    address public owner;
    
    struct User { uint id; }
    mapping(address => User) users;

    function register() public {
        // Safe: Modern solidity requires explicit data location (memory/storage)
        // and throws on uninitialized storage pointers.
        User memory user = User({id: 1});
        users[msg.sender] = user;
    }
}
```

## False-Positive Conditions & Counterexamples
- **Solidity 0.5.0+**: Uninitialized storage pointers are illegal in Solidity 0.5.0 and above; the code will not compile. Thus, any tool flagging this on modern code is outputting a false positive.
- **EIP-1967 Proxy Slots**: Upgradable proxies use `assembly { sstore(slot, value) }` to write the implementation address to a very specific, randomized slot (e.g., `_IMPLEMENTATION_SLOT`). This is completely **safe** provided the slot is a hardcoded constant and access is restricted.

## Solidity-Version Notes
- `< 0.5.0`: Highly susceptible to uninitialized storage pointers.
- `>= 0.5.0`: Uninitialized storage pointers result in compile-time errors.
- `>= 0.8.0`: Out of bounds array accesses automatically revert.

## Related Detectors
- Slither: `uninitialized-storage`, `arbitrary-send-erc20` (sometimes relates to arbitrary writes via mapping logic).
