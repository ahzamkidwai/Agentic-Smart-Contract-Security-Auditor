# MOD-006: Vault Inflation / First-Depositor Attack (ERC4626)

## Vulnerability Description
In yield-bearing vaults (like ERC4626), users deposit assets in exchange for shares. The exchange rate is calculated as `totalAssets / totalShares`. A malicious "first depositor" can deposit a tiny amount (e.g., 1 wei of Asset) to get 1 wei of Share. They then directly transfer a massive amount of Asset to the vault *without* minting shares (donating). This inflates `totalAssets` massively while `totalShares` remains 1. The exchange rate becomes extremely high. Subsequent depositors will suffer from rounding errors, effectively losing their deposits to the first depositor.

## Severity
High

## Detection Rules & Indicators
- Vaults where `shares = (assets * totalShares) / totalAssets`.
- No mitigation for the initial zero-share state (no "dead shares" minted).
- Allowing direct transfers to the vault that inflate `totalAssets`.

## Vulnerable Example
```solidity
contract VulnerableVault {
    uint public totalAssets;
    uint public totalShares;
    
    function deposit(uint amount) public {
        uint shares;
        if (totalShares == 0) {
            shares = amount; 
        } else {
            // Vulnerable: If totalAssets is artificially inflated, 
            // a depositor's shares will round down to 0!
            shares = (amount * totalShares) / totalAssets;
        }
        
        require(shares > 0, "Zero shares");
        totalAssets += amount;
        totalShares += shares;
        // ... transferFrom logic
    }
}
```

## Safe Example / Remediation
```solidity
contract SafeVault {
    uint public totalAssets;
    uint public totalShares;
    
    function deposit(uint amount) public {
        uint shares;
        if (totalShares == 0) {
            shares = amount; 
            // Fix: Mint a tiny amount of shares to the zero address (burn them)
            // This permanently prevents totalShares from returning to 0 
            // and makes inflation astronomically expensive.
            totalShares += 10**3;
            // ... mint 10**3 dead shares to address(0)
        } else {
            shares = (amount * totalShares) / totalAssets;
        }
        
        // ... 
    }
}
```

## False-Positive Conditions & Counterexamples
- **OpenZeppelin ERC4626**: Modern OpenZeppelin implementations of ERC4626 include virtual offsets to mitigate this exact attack. If the vault inherits `ERC4626` from OZ >= v4.9.0, it is **safe**.
- **Internal Accounting**: If `totalAssets` is strictly tracked internally via `deposit` and `withdraw` (ignoring force-fed tokens), the inflation attack is impossible because the attacker cannot alter `totalAssets` without minting shares.

Applies to all versions.
