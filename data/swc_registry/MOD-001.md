# MOD-001: Cross-Function Reentrancy

## Vulnerability Description
Cross-function reentrancy occurs when a vulnerable function shares state with another function. The attacker exploits an external call in the first function to re-enter the contract through the *second* function before the state has been fully updated. Even if the first function is protected by a reentrancy guard or updates its *own* state correctly, it might leave shared state inconsistent, allowing the second function to be exploited.

## Severity
High

## Detection Rules & Indicators
- Two or more functions that modify or read the same state variables (e.g., `withdraw` and `transfer`).
- An external call occurs in one function while shared state is in an intermediate/inconsistent state.
- Missing `nonReentrant` modifiers, or different locks used across shared functions.

## Vulnerable Example
```solidity
contract VulnerableBank {
    mapping(address => uint) public balances;

    // Withdraws all funds. State is updated AFTER the call.
    function withdrawAll() public {
        uint amount = balances[msg.sender];
        require(amount > 0);
        
        // Interaction
        (bool success, ) = msg.sender.call{value: amount}("");
        require(success);

        // Effect
        balances[msg.sender] = 0;
    }

    // Attacker calls this function DURING the withdrawAll() external call.
    function transfer(address to, uint amount) public {
        require(balances[msg.sender] >= amount);
        balances[msg.sender] -= amount;
        balances[to] += amount;
    }
}
```
*Attack vector: Attacker calls `withdrawAll()`. In their fallback function, before their balance is set to 0, they call `transfer()` to send their original balance to a second address they control. They get the ETH withdrawal AND keep the token balance.*

## Safe Example / Remediation
```solidity
import "@openzeppelin/contracts/security/ReentrancyGuard.sol";

contract SafeBank is ReentrancyGuard {
    mapping(address => uint) public balances;

    // Apply the same reentrancy guard to ALL functions sharing state
    function withdrawAll() public nonReentrant {
        uint amount = balances[msg.sender];
        require(amount > 0);
        
        // Even better: Update state BEFORE call (CEI pattern)
        balances[msg.sender] = 0;

        (bool success, ) = msg.sender.call{value: amount}("");
        require(success);
    }

    function transfer(address to, uint amount) public nonReentrant {
        require(balances[msg.sender] >= amount);
        balances[msg.sender] -= amount;
        balances[to] += amount;
    }
}
```

## False-Positive Conditions & Counterexamples
- **Global Reentrancy Guard**: If the contract uses OpenZeppelin's `nonReentrant` modifier on *all* state-mutating functions, cross-function reentrancy is impossible. RAG should recognize that `nonReentrant` uses a global lock (`_status`).
- **CEI strictly followed**: If the first function perfectly follows Checks-Effects-Interactions and updates all relevant state before the external call, it is **safe** from cross-function reentrancy.

## Solidity-Version Notes
Applies to all versions.
